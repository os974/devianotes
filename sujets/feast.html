Feast

Le feature store open-source de référence : une source de vérité unique pour les features de tes modèles ML, partagée entre l'entraînement et l'inference. Évite le bug classique « le modèle marchait en test, plus en prod » dû à des features calculées différemment des deux côtés.

À quoi ça sert

Une feature = une variable d'entrée d'un modèle ML (« nombre de connexions sur 30 jours », « panier moyen »…). Le problème en MLOps : on calcule ces features deux fois.

  • À l'entraînement — sur l'historique des données, en SQL ou en pandas. On a tout le temps qu'on veut.
  • À l'inference — en quasi temps réel, par utilisateur, sans accès à l'historique complet.

Si les deux calculs ne sont pas strictement identiques, on a un training-serving skew : le modèle prédit n'importe quoi en prod, et c'est très difficile à débugger.

Feast résout ça en centralisant la définition des features :

  • Définition unique — chaque feature est déclarée dans du code Python versionné dans Git. Pas de copier-coller entre notebook d'entraînement et service d'inference.
  • Offline store — les valeurs historiques pour l'entraînement (Postgres, BigQuery, S3 Parquet…).
  • Online store — un cache à faible latence pour l'inference (Redis, DynamoDB, Postgres). Sub-milliseconde par feature.
  • Materialization — Feast pousse les valeurs calculées de l'offline vers l'online sur un calendrier.
  • Point-in-time joins — à l'entraînement, récupérer les valeurs des features telles qu'elles étaient au moment de chaque exemple. Évite la fuite de données.
Ai-je vraiment besoin d'un feature store ?

Non, si tu as un seul modèle, tes features se calculent en quelques lignes pandas, et l'inference est en batch (pas en temps réel). Oui, si tu as plusieurs modèles qui partagent des features, ton inference est en production temps réel, ou ton équipe est plusieurs personnes à manipuler les mêmes features. Le coût d'apprentissage est réel, ne pas le sortir trop tôt.

Un exemple d'usage

On déclare une feature « nb commandes 30j » à partir d'une table Postgres, on demande à Feast de calculer l'historique et de pousser les dernières valeurs vers un cache Redis pour l'inference :

python (features.py) 
from datetime import timedelta
from feast import Entity, FeatureView, Field, FileSource
from feast.types import Int64, Float32

user = Entity(name="user_id", join_keys=["user_id"])

source = FileSource(
    path="data/user_stats.parquet",
    timestamp_field="event_ts",
)

user_stats = FeatureView(
    name="user_stats",
    entities=[user],
    ttl=timedelta(days=7),
    schema=[
        Field(name="nb_commandes_30j", dtype=Int64),
        Field(name="panier_moyen", dtype=Float32),
    ],
    source=source,
)
bash 
feast apply              # enregistre les définitions
feast materialize-incremental $(date -u +"%Y-%m-%dT%H:%M:%S")
                            # pousse vers l'online store
python (inference.py) 
from feast import FeatureStore

store = FeatureStore(repo_path=".")

# Récupère les dernières valeurs pour 1 utilisateur, en sub-ms
features = store.get_online_features(
    features=["user_stats:nb_commandes_30j", "user_stats:panier_moyen"],
    entity_rows=[{"user_id": "u_42"}],
).to_dict()
print(features)
# {'user_id': ['u_42'], 'nb_commandes_30j': [12], 'panier_moyen': [45.50]}

Le code de définition (features.py) est versionné, et c'est le seul endroit où les features sont définies. L'entraînement et l'inference utilisent le même code → pas de skew possible.

How-to : installer et utiliser Feast

  1. Installer Feast

    Avec UV. Selon les stores qu'on utilise, on ajoute les extras correspondants :

    bash 
    uv add feast

# Extras courants (selon les stores choisis)
uv add "feast[postgres]"      # online ou offline store Postgres
uv add "feast[redis]"         # online store Redis (faible latence)
uv add "feast[snowflake]"     # offline store Snowflake

  2. Initialiser un repo Feast

    bash 
    feast init mon_feature_store
cd mon_feature_store
ls
# feature_store.yaml    feature_repo/    data/

    feature_store.yaml contient la config (quels stores utiliser). feature_repo/ contient les définitions Python.

  3. Configurer les stores (feature_store.yaml)

    yaml 
    project: mon_projet
provider: local

registry: data/registry.db

online_store:
  type: redis
  connection_string: "localhost:6379"

offline_store:
  type: postgres
  host: localhost
  port: 5432
  database: feast
  db_schema: public
  user: app
  password: "…"

entity_key_serialization_version: 2
    Pour démarrer : tout en local

    Pour tester rapidement, l'online_store sqlite et l'offline_store file (Parquet local) suffisent. C'est ce que feast init configure par défaut. On passe à Redis/Postgres quand on déploie.

  4. Déclarer Entity, Source et FeatureView

    python 
    from datetime import timedelta
from feast import Entity, FeatureView, Field, FileSource
from feast.types import Float32, Int64, String

# Entity : la clé sur laquelle les features sont indexées
user = Entity(name="user_id", join_keys=["user_id"])

# Source : d'où viennent les valeurs historiques
src = FileSource(
    path="data/user_stats.parquet",
    timestamp_field="event_ts",
    created_timestamp_column="created",
)

# FeatureView : un groupe de features qui partagent la même source
user_stats = FeatureView(
    name="user_stats",
    entities=[user],
    ttl=timedelta(days=7),       # freshness max
    schema=[
        Field(name="nb_commandes_30j", dtype=Int64),
        Field(name="panier_moyen", dtype=Float32),
        Field(name="segment", dtype=String),
    ],
    source=src,
)

  5. Apply et materialize

    bash 
    # Enregistre les définitions dans le registry
feast apply

# Pousse les valeurs de l'offline store vers l'online store
feast materialize-incremental $(date -u +"%Y-%m-%dT%H:%M:%S")

    materialize-incremental ne re-pousse que ce qui a changé depuis la dernière fois. À lancer régulièrement (toutes les heures par exemple) via Prefect ou un cron.

  6. Récupérer pour l'entraînement (offline)

    Le point clé du point-in-time join : pour chaque exemple, Feast prend les valeurs de feature telles qu'elles étaient à ce moment précis. Évite la fuite de données (qu'on aurait avec un simple JOIN SQL).

    python 
    import pandas as pd
from feast import FeatureStore

store = FeatureStore(repo_path=".")

entity_df = pd.DataFrame({
    "user_id": ["u_1", "u_2", "u_3"],
    "event_timestamp": pd.to_datetime([
        "2026-01-10", "2026-02-15", "2026-03-22",
    ]),
})

training_df = store.get_historical_features(
    entity_df=entity_df,
    features=["user_stats:nb_commandes_30j", "user_stats:panier_moyen"],
).to_df()

  7. Récupérer pour l'inference (online)

    En prod, on veut les dernières valeurs, en sub-ms :

    python 
    features = store.get_online_features(
    features=["user_stats:nb_commandes_30j", "user_stats:panier_moyen"],
    entity_rows=[{"user_id": "u_42"}],
).to_dict()

# Puis on passe les features au modèle
prediction = model.predict([[
    features["nb_commandes_30j"][0],
    features["panier_moyen"][0],
]])

  8. Lancer le serveur Feast (optionnel)

    Pour exposer l'online store derrière une API REST/gRPC consommable par n'importe quel service (pas que Python) :

    bash 
    feast serve --host 0.0.0.0 --port 6566

    Particulièrement utile dans un projet microservices où l'inference n'est pas forcément en Python.

Feast et le reste de l'écosystème

  • PostgreSQL — Postgres est le choix par défaut comme offline store (analytique) et peut aussi servir d'online store si les latences sont OK. Très bonne combinaison pour un projet de taille moyenne.
  • Redis — l'online store de choix en prod : sub-milliseconde par feature, gère des milliers de lookups/seconde sans broncher.
  • MLflow — pattern typique : à l'entraînement, on récupère les features avec get_historical_features, on les passe au modèle, on log le tout dans MLflow. La feature view utilisée est loggée comme tag.
  • Prefect — orchestre la materialize-incremental sur un calendrier (typiquement toutes les heures). Sans orchestration, l'online store devient stale.
  • FastAPI — pattern d'inference : FastAPI reçoit une requête, fait un get_online_features, passe à un modèle scikit-learn ou PyTorch, renvoie la prédiction. Le tout sous 50 ms.
  • DVC — versionner le snapshot Parquet qui sert de source à Feast. Combo classique : DVC pour les datasets « bruts », Feast pour les features dérivées prêtes à l'emploi.
  • Evidently — surveiller la dérive des features stockées dans Feast. La feature store fournit le « dataset courant », Evidently le compare au dataset d'entraînement de référence.
Le piège : Feast avant qu'on en ait besoin

Feast brille quand on a plusieurs modèles, plusieurs équipes, inference temps réel. Pour un projet pédagogique avec un modèle scikit-learn et de l'inference batch, c'est over-engineering. Garde-le en tête pour ton projet de fin de formation si tu veux montrer une vraie chaîne MLOps mature, mais ne le déploie pas avant que la douleur du training-serving skew se manifeste.
