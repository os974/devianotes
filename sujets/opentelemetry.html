OpenTelemetry

Le standard ouvert d'observabilité moderne, qui unifie traces, métriques et logs sous une même API. Permet de suivre une requête à travers plusieurs services et de comprendre où elle passe son temps. Le troisième pilier qui manque souvent quand on a déjà Prometheus + Grafana.

À quoi ça sert

En microservices, une requête utilisateur passe par plusieurs services : front → API → base de données → service de mail. Quand « le bouton est lent », tu veux savoir lequel est en cause. Avec seulement les logs de chaque service, c'est une enquête fastidieuse. Avec les traces distribuées : tu vois en un graphique la requête entière, le temps passé à chaque étape.

OpenTelemetry (« OTel ») normalise trois signaux :

  • Traces — la requête qui traverse N services, découpée en spans (= unités de travail) reliés en arbre. Réponse à « où passe le temps ? ».
  • Métriques — comme Prometheus : compteurs, gauges, histogrammes. Réponse à « combien de fois ? combien de temps en moyenne ? ».
  • Logs — corrélés aux traces (chaque log porte le trace_id). Réponse à « qu'est-ce qui s'est passé précisément ? ».

OTel se compose de :

  • SDK Python — l'instrumentation qui produit les signaux dans ton code.
  • OTLP — le protocole standard pour exporter les signaux (HTTP ou gRPC).
  • OTel Collector — agent qui reçoit les signaux, les transforme, les ré-exporte vers le backend de ton choix.
  • Backends — Jaeger, Grafana Tempo, Honeycomb, Datadog… OTel est vendor-neutral, tu changes de backend sans toucher au code.
Traces, métriques, logs : les 3 piliers

Logs (cf. logging, Loguru, Loki) : des événements ponctuels, riches en détail. Métriques (cf. Prometheus) : des valeurs agrégées dans le temps, bonnes pour le monitoring et les alertes. Traces : le parcours d'une requête à travers N services, indispensable en microservices. Les trois sont complémentaires — OpenTelemetry permet de les corréler entre eux via un identifiant commun (trace_id).

Un exemple d'usage

Instrumenter une appli FastAPI pour tracer chaque requête sans modifier la moindre ligne de code métier (instrumentation automatique) :

bash 
uv add opentelemetry-distro opentelemetry-exporter-otlp \
       opentelemetry-instrumentation-fastapi
uv run opentelemetry-bootstrap -a install

# Lancer l'app avec instrumentation auto
uv run opentelemetry-instrument \
    --traces_exporter otlp \
    --service_name mon-api \
    --exporter_otlp_endpoint http://localhost:4317 \
    uvicorn main:app

Sans toucher au code main.py, chaque requête HTTP est désormais tracée : durée, méthode, statut, et tous les appels HTTP sortants ou requêtes SQL inclus. Les traces partent en OTLP vers l'endpoint (typiquement un Collector ou Jaeger en local), où tu peux les visualiser en arbre. Magique pour debugger une lenteur quand on ne sait pas par où commencer.

How-to : installer et utiliser OpenTelemetry

  1. Lancer un backend de traces en local

    Le plus simple : Jaeger all-in-one dans Docker (UI + collector + storage en un conteneur). Pour de la prod, on préfère Grafana Tempo qui s'intègre dans la même UI que Prometheus et Loki.

    bash 
    docker run -d --name jaeger \
  -p 16686:16686 \
  -p 4317:4317 \
  -p 4318:4318 \
  jaegertracing/all-in-one:latest

    UI accessible sur http://localhost:16686. 4317 = OTLP gRPC, 4318 = OTLP HTTP.

  2. Installer le SDK Python

    Avec UV, deux paquets clés et un par framework instrumenté :

    bash 
    uv add opentelemetry-distro                      # API + SDK + bootstrap
uv add opentelemetry-exporter-otlp              # exporter OTLP

# Instrumentations automatiques (selon ce que ton app utilise)
uv add opentelemetry-instrumentation-fastapi
uv add opentelemetry-instrumentation-httpx
uv add opentelemetry-instrumentation-sqlalchemy
uv add opentelemetry-instrumentation-logging

# OU : détection auto de toutes les libs installées
uv run opentelemetry-bootstrap -a install

  3. Instrumentation automatique (zéro code)

    Le plus magique : tu lances ton app via opentelemetry-instrument, qui « monkey-patch » les libs courantes pour produire des spans à ta place.

    bash 
    opentelemetry-instrument \
    --traces_exporter otlp \
    --metrics_exporter none \
    --service_name mon-api \
    --exporter_otlp_endpoint http://localhost:4317 \
    uvicorn main:app --host 0.0.0.0 --port 8000

    FastAPI, httpx, requests, SQLAlchemy, psycopg, pymongo et d'autres sont automatiquement instrumentés. Pour chaque requête HTTP, un span racine est créé et tous les appels internes y sont rattachés.

    Configuration par variables d'environnement

    On peut aussi tout configurer via env vars (plus propre en Docker) : OTEL_SERVICE_NAME, OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_TRACES_EXPORTER, OTEL_PROPAGATORS… Documenté côté OTel et Pydantic Settings peut les charger dans ton app.

  4. Instrumentation manuelle (spans custom)

    Pour tracer une fonction métier précise, on crée un span à la main :

    python 
    from opentelemetry import trace

tracer = trace.get_tracer(__name__)

def traiter_commande(commande_id: str) -> dict:
    with tracer.start_as_current_span("traiter_commande") as span:
        span.set_attribute("commande.id", commande_id)

        with tracer.start_as_current_span("valider"):
            valider(commande_id)

        with tracer.start_as_current_span("payer"):
            payer(commande_id)

        return {"status": "ok"}

    Le span traiter_commande englobe deux spans enfants valider et payer. Dans l'UI Jaeger, tu vois l'arbre complet avec les durées de chaque étape. Les attributs (set_attribute) sont indexés et cherchables (« montre-moi toutes les commandes en erreur de l'utilisateur X »).

  5. Corréler logs et traces

    L'avantage tueur d'OTel : chaque log peut porter le trace_id de la requête en cours. Tu cliques sur un span lent dans Jaeger, tu sautes dans Loki sur les logs de cette trace exacte.

    python 
    from opentelemetry.instrumentation.logging import LoggingInstrumentor
LoggingInstrumentor().instrument(set_logging_format=True)

import logging
logging.basicConfig(level=logging.INFO)
log = logging.getLogger(__name__)

log.info("Traitement commencé")
# sortie : "2026-05-16 ... [trace_id=abc123 span_id=def456] Traitement commencé"

  6. Propagation entre services

    Quand le service A appelle le service B en HTTP, OTel injecte automatiquement le trace_id dans les en-têtes (traceparent). Le service B le récupère et continue la trace. Résultat : une vue unifiée de la requête traversant N services.

    Ça marche tout seul si les deux services utilisent opentelemetry-instrumentation-httpx (ou -requests, -grpc…) côté client, et -fastapi (ou -flask) côté serveur.

  7. OTel Collector (recommandé en prod)

    En prod, on n'envoie pas les traces directement de l'app vers le backend. On les envoie à un Collector (sidecar ou daemon) qui s'occupe du buffering, du sampling, de l'enrichissement, puis ré-exporte vers le backend.

    Avantage : tu changes de backend (Jaeger → Tempo → Datadog) sans toucher au code des apps. Tu peux aussi décider à la volée d'envoyer 100% des erreurs et 10% des requêtes normales (sampling intelligent).

    bash (Docker) 
    docker run -d --name otelcol \
  -p 4317:4317 -p 4318:4318 \
  -v $(pwd)/otelcol-config.yaml:/etc/otelcol/config.yaml \
  otel/opentelemetry-collector:latest \
  --config=/etc/otelcol/config.yaml

  8. Visualiser dans Grafana (combo complet)

    La stack moderne complète :

    • OTel SDK + Collector dans les apps envoient logs + métriques + traces.
    • Loki stocke les logs.
    • Prometheus (ou Mimir) stocke les métriques.
    • Tempo stocke les traces (OSS, équivalent Jaeger côté backend).
    • Grafana affiche les trois sources et permet de naviguer de l'une à l'autre (cliquer sur un span lent → voir les logs associés).

OpenTelemetry et le reste de l'écosystème

  • Prometheus — OTel peut exporter ses métriques directement au format Prometheus, ou passer par un Collector. Les deux mondes convergent.
  • Grafana — Grafana affiche traces (Tempo), logs (Loki) et métriques (Prometheus) dans la même UI, avec navigation croisée. Couplé à OTel, c'est l'observabilité moderne complète.
  • Loki — quand on logge en JSON avec le trace_id dedans, on peut sauter d'un span Tempo vers les logs Loki correspondants en un clic.
  • FastAPI — opentelemetry-instrumentation-fastapi instrumente toutes les routes sans une ligne de code. Idem pour -flask, -django.
  • httpx / SQLAlchemy / Redis — instrumentations disponibles. Tous les appels sortants se rattachent automatiquement au span courant — propagation distribuée gratuite.
  • Docker / Kubernetes — le Collector se déploie comme un service Docker ou un DaemonSet Kubernetes (un par nœud), avec toutes les apps qui pushent vers lui.
  • logging / Loguru — la corrélation log ↔ trace via trace_id est ce qui rend OTel vraiment puissant. Sans elle, tu retombes dans le debug en regardant les logs un par un.
Quand OTel devient indispensable

Sur une appli monolithique, OTel apporte un confort marginal — les logs suffisent souvent. Dès qu'il y a plus de 2 services qui s'appellent, OTel devient le seul moyen sain de comprendre où passe le temps. C'est exactement le problème typique d'une archi microservices comme boxmicroservices.
