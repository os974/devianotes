Chroma

La base de données vectorielle Python-first : un pip install, trois lignes, et tu as un index sémantique fonctionnel. Idéale pour prototyper un RAG, faire un POC ou démarrer avec LangChain et LlamaIndex — en pendant simple de Qdrant qu'on utilisera plutôt en production.

À quoi ça sert

Chroma sert à stocker des embeddings (vecteurs) et retrouver les plus proches d'une requête, comme toutes les bases vectorielles. Sa particularité : tout passe par une lib Python embarquée, sans serveur à lancer. On l'utilise comme on utilise SQLite pour les bases SQL — c'est le « SQLite des vector DBs ».

Quelques cas typiques :

  • POC / prototype RAG — un notebook Jupyter, 500 documents, on veut un index sémantique sans monter un service.
  • Mémoire d'agent LLM — stocker les conversations passées pour les retrouver par similarité plus tard.
  • Recherche dans une doc technique — indexer un site, un wiki interne, des PDFs, et brancher un LLM dessus.
  • Tests unitaires de pipeline RAG — en mode in-memory, Chroma se reset à chaque pytest.
Chroma ou Qdrant ?

Chroma = embarqué, Python-only, ultra-simple à démarrer, écrit en Python (avec du SQLite/DuckDB en dessous pour le stockage). Parfait pour POCs, démos, petits projets RAG (jusqu'à ~10⁶ vecteurs). Qdrant = serveur dédié, écrit en Rust, scalable, distribué, REST + gRPC. À choisir dès qu'on vise la prod ou les gros volumes. Règle simple : Chroma pour démarrer, Qdrant quand ça grossit. Et bonne nouvelle : LangChain et LlamaIndex supportent les deux avec quasiment la même API — la migration coûte 3 lignes.

Un exemple d'usage

On installe Chroma, on crée une collection, on y ajoute trois documents, et on cherche par similarité. Aucun serveur, aucun Docker.

bash 
uv add chromadb
python 
import chromadb

# Client embarqué, persistant sur disque
client = chromadb.PersistentClient(path="./chroma_data")

# Créer (ou récupérer) une collection
collection = client.get_or_create_collection(name="docs")

# Ajouter trois documents — Chroma calcule lui-même les embeddings
collection.add(
    ids=["d1", "d2", "d3"],
    documents=[
        "Python est un langage de programmation interprété.",
        "FastAPI permet de créer des APIs Python rapides.",
        "La pâte à crêpes se fait avec farine, œufs et lait.",
    ],
    metadatas=[
        {"source": "wiki", "lang": "fr"},
        {"source": "doc", "lang": "fr"},
        {"source": "recette", "lang": "fr"},
    ],
)

# Recherche sémantique
results = collection.query(
    query_texts=["comment faire une API en Python ?"],
    n_results=2,
)

for doc, dist in zip(results["documents"][0], results["distances"][0]):
    print(round(dist, 3), doc)
# > 0.41 FastAPI permet de créer des APIs Python rapides.
# > 0.62 Python est un langage de programmation interprété.

À noter : Chroma renvoie des distances (plus petit = plus proche), là où Qdrant renvoie des scores (plus grand = plus proche). Petite habitude à prendre quand on jongle entre les deux. Le modèle d'embedding par défaut est all-MiniLM-L6-v2 (sentence-transformers), téléchargé automatiquement au premier appel.

How-to : installer et utiliser Chroma

  1. Installer chromadb

    Avec UV. Aucun service à lancer, c'est une lib Python pure (avec du natif en dessous pour la perf) :

    bash 
    uv add chromadb
    Premier import = téléchargement

    Au premier import chromadb qui calcule un embedding, sentence-transformers télécharge le modèle par défaut (~90 MB). Prévois la bande passante, ou pré-télécharge le modèle dans ton Dockerfile pour les builds reproductibles.

  2. Choisir un client : in-memory, persistant, ou serveur

    Trois modes selon ce que tu veux faire :

    python 
    import chromadb

# 1) En mémoire — tests, notebooks éphémères
client = chromadb.Client()

# 2) Persistant sur disque — apps locales, POCs, prod légère
client = chromadb.PersistentClient(path="./chroma_data")

# 3) Mode serveur (Chroma server lancé séparément)
client = chromadb.HttpClient(host="localhost", port=8000)

    Le mode persistant est le défaut le plus utile : tu fermes ton process, tu le relances, ta base est toujours là (un dossier avec un SQLite + des fichiers d'index).

  3. Créer ou récupérer une collection

    Une collection est l'équivalent d'une table dans une base SQL : c'est là que vivent les documents et leurs embeddings.

    python 
    # get_or_create_collection est idempotent (le plus utile)
collection = client.get_or_create_collection(
    name="docs",
    metadata={"hnsw:space": "cosine"},   # cosine, l2, ip
)

# Lister les collections
client.list_collections()

# Supprimer
client.delete_collection(name="docs")

  4. Ajouter, modifier, supprimer des documents

    python 
    # add — échoue si un id existe déjà
collection.add(
    ids=["d1", "d2"],
    documents=["texte un", "texte deux"],
    metadatas=[{"source": "wiki"}, {"source": "doc"}],
)

# upsert — insère ou met à jour selon l'id (le plus pratique)
collection.upsert(
    ids=["d1"],
    documents=["texte un mis à jour"],
)

# delete par id
collection.delete(ids=["d2"])

# Compter
collection.count()

  5. Recherche sémantique avec filtres

    Comme avec Qdrant, on peut filtrer sur les métadonnées en plus de la similarité — par exemple pour ne chercher que dans une langue ou une source précise :

    python 
    results = collection.query(
    query_texts=["comment faire une API ?"],
    n_results=3,
    where={"lang": "fr"},                          # filtre exact
    where_document={"$contains": "API"},        # filtre full-text
)

# Filtre composé
results = collection.query(
    query_texts=["recettes"],
    n_results=5,
    where={"$and": [
        {"lang": "fr"},
        {"source": {"$ne": "draft"}},
    ]},
)

# results contient : ids, documents, metadatas, distances, embeddings
for doc, meta, dist in zip(
    results["documents"][0],
    results["metadatas"][0],
    results["distances"][0],
):
    print(dist, meta["source"], doc)

  6. Utiliser ton propre embedding (Ollama, Hugging Face, OpenAI)

    Par défaut, Chroma utilise sentence-transformers (all-MiniLM-L6-v2, 384 dimensions). On peut brancher n'importe quel modèle via une embedding function. Exemple avec Ollama en local :

    python 
    from chromadb.utils.embedding_functions import OllamaEmbeddingFunction

ef = OllamaEmbeddingFunction(
    model_name="nomic-embed-text",
    url="http://localhost:11434/api/embeddings",
)

collection = client.get_or_create_collection(
    name="docs",
    embedding_function=ef,
)

# add/query utilisent maintenant Ollama au lieu de sentence-transformers
collection.add(ids=["d1"], documents=["…"])
    L'embedding function est figée par collection

    Une fois une collection créée avec un modèle d'embedding, il faut conserver le MÊME modèle pour les recherches — sinon les vecteurs vivent dans des espaces différents et la similarité n'a plus de sens. Si tu changes de modèle, recrée la collection.

  7. Ajouter ses propres vecteurs (skip l'embedding auto)

    Pour des embeddings déjà calculés ailleurs, on passe embeddings= au lieu de documents= :

    python 
    collection.add(
    ids=["d1", "d2"],
    embeddings=[[0.1, 0.2, ...], [0.3, 0.4, ...]],
    documents=["texte un", "texte deux"],
    metadatas=[{"source": "a"}, {"source": "b"}],
)

results = collection.query(
    query_embeddings=[[0.15, 0.25, ...]],
    n_results=2,
)

  8. Lancer Chroma en mode serveur (optionnel)

    Si plusieurs services doivent partager la même base, on lance Chroma comme serveur. Avec Docker :

    bash 
    docker run -d --name chroma \
  -p 8000:8000 \
  -v chroma_data:/chroma/chroma \
  chromadb/chroma:latest

    Côté client Python : chromadb.HttpClient(host="localhost", port=8000). À ce stade on est sur le terrain de Qdrant — qui est généralement un meilleur choix pour ce cas.

Chroma et le reste de l'écosystème

  • Qdrant — le grand frère prod-ready. Même concept (collections, embeddings, recherche ANN + filtres), mais serveur dédié en Rust. À choisir dès qu'on dépasse quelques millions de vecteurs ou qu'on veut un service partagé entre plusieurs apps.
  • LangChain — Chroma est l'un des vector stores de référence de LangChain. Un Chroma.from_documents(docs, embeddings) et tu as un retriever prêt à brancher dans une chain RAG.
  • LlamaIndex — même intégration que LangChain, via ChromaVectorStore. Très utilisé en démo car l'ensemble tourne sans Docker.
  • Ollama — pour les embeddings en local. La combinaison Chroma + Ollama est le stack RAG « 100% local, gratuit » le plus simple à mettre en place.
  • Hugging Face — l'embedding function par défaut de Chroma vient de sentence-transformers, qui est lui-même un projet HF. Tu peux charger n'importe quel modèle Sentence-BERT depuis le hub.
  • FastAPI — pour exposer un RAG basé sur Chroma comme service web : on instancie le client au démarrage, chaque requête fait un collection.query(...). Attention à la concurrence : Chroma persistant écrit dans un SQLite, donc pas idéal pour des écritures parallèles intensives.
  • DuckDB / SQLite — Chroma s'appuie sur eux pour le stockage des métadonnées et des index. C'est ce qui rend la base si légère à embarquer.
Quand migrer de Chroma à Qdrant ?

Trois signaux pour passer à Qdrant : (1) tu dépasses ~1 million de vecteurs et les requêtes ralentissent, (2) plusieurs services ont besoin d'écrire en parallèle dans la même base, (3) tu veux de la réplication / sharding. Avant ces seuils, Chroma est largement suffisant — et la migration est triviale puisque LangChain et LlamaIndex abstraient le vector store.
