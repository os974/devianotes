Retex — Explorer les OCR et LLM pour un POC KYC

Comment quatre moteurs d'OCR ont été comparés sur des cartes d'identité, des passeports et des KBIS, avec un LLM en aval pour structurer le résultat. Ce qui marche, ce qui rate, et pourquoi aucun moteur seul ne suffit en production.

Ce qu'on cherche dans ce retex

Non pas quel OCR utiliser dans l'absolu — la réponse dépend trop du contexte. Plutôt : quelles questions se poser avant de choisir, quelles erreurs éviter, et comment structurer l'expérimentation pour aboutir à une décision défendable. Les leçons sont volontairement génériques pour servir hors du KYC.

1. Le contexte

Objectif : un POC capable de transformer une photo de carte nationale d'identité, de passeport ou un PDF de KBIS en JSON structuré (nom, prénoms, numéro, dates, SIREN, adresse, etc.). Cible : un usage KYC (Know Your Customer) où l'extraction doit être fiable, auditable, et conforme RGPD.

Les deux briques techniques :

  • Un moteur OCR pour transformer pixels en texte brut.
  • Un LLM pour structurer le texte brut en JSON respectant un schéma fixe.

Au démarrage : un seul OCR (PaddleOCR) et un seul LLM (mistral-small-latest). À la fin : quatre OCR branchables via un flag --engine, et un prompt LLM durci pour empêcher les hallucinations. La trajectoire est plus intéressante que la destination.

2. Ce qu'on voulait

  • Qualité prod : viser > 95 % de champs corrects sur les documents réels (cible KYC industrielle).
  • Conformité RGPD : minimiser les données envoyées à des tiers (les CNI contiennent visage, signature, hologrammes — données sensibles).
  • Latence acceptable : on est sur des flux KYC asynchrones, mais < 30 s par document reste un seuil psychologique.
  • Comparaison équitable : pouvoir benchmarker plusieurs moteurs sur les mêmes échantillons, sans qu'un run en écrase un autre.

3. La structure d'archi qu'on a fini par adopter

L'OCR est devenu une interface dans le code, avec une signature unique extract_text(file_path) → str. Chaque moteur est un module Python autonome, importé à la volée pour ne pas payer le coût de chargement d'un moteur qu'on n'utilise pas.

python — sélecteur de moteur OCR 
OCR_ENGINES = ("paddleocr", "mistral", "doctr", "paddleocr-vl")

def _load_ocr_engine(engine):
    if engine == "paddleocr":
        from ocr import extract_text
        return extract_text
    if engine == "mistral":
        from ocr_mistral import extract_text
        return extract_text
    # … doctr, paddleocr-vl

Sortie rangée dans outputs/<engine>/ pour permettre le diff côte à côte sans écrasement. Le pipeline aval (MRZ-first + structuration LLM) est indépendant du moteur OCR choisi : seule la première étape change. C'est ce découplage qui a rendu le benchmark possible.

4. Les leçons (par ordre d'apparition)

Leçon 1 — Les bibliothèques OCR cassent leur API en mineure

Symptôme : la sortie OCR contient n / a / o / t / o / e / e / e / e… (une lettre par ligne).

Cause : PaddleOCR 3.5 a changé silencieusement son format de retour. .ocr() rend maintenant un OCRResult (dict) avec une clé rec_texts, alors qu'avant c'était une liste [bbox, (text, score)]. L'ancien code [line[1][0] for line in result[0]] itérait désormais sur les clés du dict (input_path, page_index, doc_preprocessor_res…) et prenait leur 2ᵉ caractère. D'où n, a, o…

Leçon générique : verrouiller la version d'une bibliothèque OCR (ou de toute lib ML) dans pyproject.toml n'est pas du zèle — c'est une protection contre des bris d'API qui ne lèvent même pas d'exception. Si une lib renvoie soudain des données absurdes mais ne plante pas, regarde d'abord ses notes de release.

Leçon 2 — Les paramètres par défaut d'un OCR sont rarement adaptés à ton cas

Symptôme : sur une CNI française au format nouveau, PaddleOCR avec ses paramètres par défaut sort nom: SERAN au lieu de MARTIN et prenom: Pa rl au lieu de Maëlis-Gaëlle, Marie. Le sexe n'est même pas détecté.

Cause : deux paramètres internes ont un impact massif et restent largement ignorés :

  • text_det_limit_side_len (défaut 960) : la résolution interne utilisée pour la détection. À 960 px, une A4 scannée à 300 DPI (~2480 px) est downscalée avant la détection. Les petits caractères des CNI deviennent illisibles.
  • text_det_unclip_ratio (défaut 1.5) : le facteur d'expansion des boîtes de détection. Sur les polices stylisées de sécurité, les ascendantes et descendantes sont coupées si le ratio est trop serré.

Avec limit_side_len=1920, unclip_ratio=2.0, plus un pré-traitement OpenCV (CLAHE + denoising léger), la même CNI rend MARTIN / Maëlis-Gaëlle, Marie / F sans erreur. 4 paramètres ont déplacé l'extraction de 0 % à 100 % sur le sample le plus dur.

Leçon générique : avant de conclure « cette bibliothèque ne marche pas pour mon cas », passe une demi-heure dans sa doc des paramètres. Les défauts sont souvent calibrés pour des benchmarks anglais ou chinois, pas pour ton domaine spécifique.

Leçon 3 — Choisir « plus puissant » sans réfléchir peut empirer les choses

Symptôme : en bascule de latin_PP-OCRv5_mobile_rec vers PP-OCRv5_server_rec (le modèle multilingue « server »), la sortie devient HIAARANRANREEINASIERTE, NALAE, SEIEREERAE… des séquences de caractères aléatoires.

Cause : le modèle « server » est multilingue (latin + CJK + arabe + cyrillique). Sur un fond holographique bruité, il invente des patterns en piochant dans son vocabulaire entier. Le modèle latin spécialisé, plus contraint, échouait de manière reconnaissable (« SERAN » au lieu de « MARTIN ») ; le modèle plus puissant échoue de manière incompréhensible.

Leçon générique : un modèle plus gros ou plus polyvalent n'est pas forcément meilleur pour ton cas. Spécialiser (alphabet latin, langue cible) restreint l'espace de sortie et rend les erreurs interprétables. Tu peux corriger une erreur cohérente, pas une hallucination.

Leçon 4 — Quand un document a une zone machine-readable, c'est l'or pur

Les CNI françaises nouveau format (≥ août 2021) et les passeports ont une MRZ (Machine-Readable Zone) : une ou plusieurs lignes de texte à police standardisée (OCR-B), avec des positions fixes et des checksums intégrés.

On a basculé l'architecture sur le pattern MRZ-first :

  • Si une MRZ est détectée et son score de validation est bon → ses champs structurés (numéro, dates, sexe, nationalité) sont la vérité. Le LLM n'intervient plus que pour récupérer la graphie accentuée des noms (la MRZ est ASCII pur — MAELIS<GAELLE).
  • Si la MRZ n'est pas exploitable → fallback sur le pipeline OCR + LLM standard.

Leçon générique : avant d'attaquer un document avec de l'OCR généraliste, demande-toi s'il existe une sous-zone conçue pour être lue par machine : codes-barres, QR, MRZ, RIB structuré, tableaux à colonnes fixes. Une lecture déterministe sur une zone structurée bat presque toujours un OCR généraliste sur la zone visuelle, et est plus défendable en audit.

Leçon 5 — Aucune source n'est fiable à 100 %, même la MRZ

Symptôme : sur un passeport, la MRZ extrait 9ORFO2331 au lieu de 90RF02331.

Cause : le moteur OCR sous-jacent à passporteye (Tesseract) confond O et 0. Le checksum ICAO compense partiellement mais pas toujours.

Surprise : les autres OCR (PaddleOCR-VL notamment) lisent correctement ce numéro 90RF02331 dans la zone visuelle. La MRZ (déterministe a priori) est ici moins fiable que l'OCR de la zone visuelle.

Leçon générique : traite chaque source comme une opinion, pas une vérité. Si tu as plusieurs sources sur le même champ (MRZ + visuel), croise-les et signale les divergences. Le « champion unique » est un mythe industriel — on est en train d'implémenter une cross-validation par champ pour Phase 3.

Leçon 6 — Le LLM aval hallucine quand l'OCR est ambigu

Symptômes observés :

  • OCR rend SL avenue → LLM extrait 51 avenue (le LLM devine que « SL » est probablement un code postal mal lu).
  • OCR rend 42 a Duris → LLM extrait 42 avenue Duris (le LLM reconstruit un mot manquant).
  • OCR rend un texte riche → LLM rend representant_legal comme un objet imbriqué au lieu d'une string, alors que le schéma demande une string.

Cause : un LLM, instruit de structurer du texte en JSON, est entraîné à produire des réponses cohérentes et complètes. En l'absence d'instruction explicite, il complète les trous plutôt que de mettre null.

Solution : durcir le prompt avec des règles explicites :

extrait du prompt durci 
RÈGLES STRICTES :
- Chaque champ DOIT être une chaîne de caractères (string) ou null.
  INTERDICTION de retourner un objet imbriqué.
- NE COMPLÈTE PAS un champ partiel : si l'OCR montre "X4RTBPFW"
  tronqué, retourne ce que tu vois sans inventer la suite.
- NE RECONSTRUIS PAS de mots manquants par déduction : si l'OCR
  dit "a Duris" sans "rue/avenue", retourne "a Duris" tel quel
  ou null — pas "rue Duris" ni "avenue Duris".
- N'INVENTE PAS de chiffres : si l'OCR dit "SL avenue", garde tel
  quel ou null — ne suppose pas que "SL" est "51".

Effet de bord à anticiper : le prompt durci élimine les hallucinations dangereuses mais introduit aussi une over-prudence sur les nettoyages légitimes (le LLM ne nettoie plus le bruit terminal d'une MRZ mal lue, ne corrige plus un macron OCR en tréma). Le bon réflexe : déplacer ces nettoyages côté code déterministe (regex, post-traitement) plutôt que de compter sur le LLM pour ce travail.

Leçon 7 — Aucun moteur OCR n'est universel sur des documents variés

Quatre moteurs testés sur 5 échantillons (CNI, passeport, KBIS) — 29 champs au total :

  • docTR (Mindee, local) : 90 % de champs corrects
  • PaddleOCR tuné (local) : 86 %
  • PaddleOCR-VL-1.5 (VLM local 0.9 B) : 83 %
  • Mistral vision (API multimodale) : 79 %

Mais surtout : ils ne ratent jamais les mêmes champs. Sur un sample où PaddleOCR confond un label avec une valeur (nom: Sumame), docTR sort le bon nom (MARTIN) et le bon numéro. Sur un autre où Mistral hallucine un NATANA au lieu de NATACHA, PaddleOCR le lit correctement.

Conclusion industrielle : ne pas chercher le moteur miracle. Construire une architecture multi-moteurs avec vote ou fallback par champ. Avec un agrégateur simple (vote majoritaire + score de confiance), on peut viser 95 %+ de précision sans toucher aux moteurs individuels.

Leçon générique : quand aucun candidat n'atteint seul le seuil cible, l'ensemble peut le faire — à condition que les erreurs des candidats soient décorrélées. C'est exactement le pari du multi-moteurs ici.

Leçon 8 — Le verrou n'est pas le moteur, c'est les données et l'évaluation

Après quatre moteurs benchmarkés, l'instinct est de continuer à en tester un cinquième, un sixième. Mauvais réflexe.

Sur 5 échantillons (dont 3 spécimens marqués SPÉCIMEN, 1 synthétique de 1.5 KB), les écarts entre moteurs reposent sur 1-3 différences sur 29 champs. Statistiquement, c'est dans le bruit. Le ranking actuel pourrait s'inverser sur les 10 documents suivants.

Les vrais verrous identifiés :

  • Volume de données : sans 30-50 vrais documents anonymisés, aucune conclusion statistique n'est défendable.
  • Automatisation de l'évaluation : comparer JSON par JSON à la main ne scale pas au-delà de 10 samples. Il faut un eval.py avec golden JSON + calcul d'accuracy par champ.
  • Qualité d'image en entrée : sur un PNG haute résolution, tous les moteurs convergent. Sur un JPG fortement compressé, les écarts apparaissent. Le levier opérationnel le plus puissant n'est pas technique, c'est la consigne UX au moment de la capture.

Leçon générique : avant d'ajouter un candidat de plus à un benchmark, demande-toi si tu as assez de données pour distinguer les candidats déjà présents. Quand le ROI sur « tester un de plus » devient plat, le ROI sur « avoir plus de données » et « automatiser le scoring » devient lui exponentiel.

5. Le résultat final

Le pipeline finalisé est interchangeable au niveau du moteur OCR, garde une étape MRZ-first quand c'est applicable, et passe par un LLM durci pour la structuration :

schéma du pipeline 
Document (image / PDF)
        ↓
[Moteur OCR sélectionnable : paddleocr | doctr | mistral | paddleocr-vl]
        ↓
Texte brut → outputs/<engine>/<sample>_ocr.txt
        ↓
[Pour CI / passeport : tentative MRZ via passporteye + Tesseract]
        │                       │
   pas de MRZ              MRZ exploitable
        │                       │
   prompt complet         prompt « accents-only » (LLM ne touche qu'aux diacritiques)
        ↓                       ↓
[LLM Mistral Small en mode JSON natif, prompt durci anti-hallucination]
        ↓
[Validation schéma + normalisation : SIREN, sexe, nationalité]
        ↓
JSON final → outputs/<engine>/<sample>_<doc_type>.json

L'organisation des sorties par moteur (un sous-dossier chacun) rend la comparaison triviale : il suffit de comparer outputs/paddleocr/martin_ci.json avec outputs/doctr/martin_ci.json pour voir où chaque moteur trébuche.

6. Ce qu'il reste à faire (Phase 3 et au-delà)

  • Cross-validation MRZ ↔ OCR visuel : utiliser un pattern alphanumérique attendu (regex) pour départager quand les deux sources divergent sur le numéro de document.
  • Pydantic strict sur les schémas : fermer définitivement le risque de dict imbriqué qui se faufile malgré le prompt durci.
  • Eval automatisée : eval.py avec golden JSON par sample, calcul d'accuracy par champ. Indispensable avant d'élargir à 30+ documents.
  • Ensemble multi-moteurs : agrégateur de vote majoritaire ou de score de confiance par champ. Conclusion logique de la Leçon 7 mais pas encore implémentée.
